## 8. 技术调研记录

> 记录"已知但暂不处理"的技术问题：现象、根因、候选方案与取舍，给未来优化留依据。
> 每条必须写清**重新评估的触发条件**，否则容易变成永久的将就。

### X1 console 提示符与日志输出互冲（esp_console + ESP_LOG 共用 UART）

- **状态**：已确认可接受，暂不处理（2026-10-30，T0.5 真机验收时发现）
- **现象**：REPL 启动后 `esp-ai>` 提示符被后续日志追加成 `esp-ai>I (123) APP: ...`；输入过程中到达的日志会被整行重绘擦掉，日志与命令输出交错，日志密集时更明显。
- **触发条件**：REPL 启动后任一任务继续打日志。P0 是初始化日志；P1 接 WiFi/WS 心跳后频率明显上升；P4 音乐状态日志也会持续输出。
- **根因**（两处，缺一不可）：
  1. **共用同一 sink**：`esp_log_write()` 的默认输出函数就是 `vprintf`（IDF `components/log/src/os/log_write.c`），与 `printf` 一样经 stdout → VFS → UART 驱动写出；物理上只有一条串口通道。
  2. **没有仲裁**：linenoise 只在每轮读行前打印一次提示符，输入时用 `\r` + ANSI 序列整行重绘（`linenoiseRefresh`），不知道期间有外部写入，也不做互斥。
- **不是设计缺陷**：命令输出刻意走 `printf`（不受 `log <tag> <level>` 过滤、无时间戳/标签前缀），日志走 `ESP_LOG`（可分级过滤）；本条只讨论显示层交错，不改变这个分工。
- **影响**：纯显示层，不影响命令执行与输入；影响人工调试可读性，以及将来脚本/产测解析 console 输出。
- **现有缓解（零成本）**：开机等 2~3 秒再交互；或先 `log * warn` 降噪。
- **候选方案**：

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| A 接受 + 降噪 | `log <tag> warn` / `log * warn` | 0 | 日志信息变少，需要时再开 |
| B `diag_init()` 后移 | 提示符最后出现 | 极小 | 初始化期间不能敲命令（崩溃日志仍可见，日志不依赖 REPL） |
| C `linenoiseSetDumbMode(1)` | 关掉整行编辑/重绘 | 极小 | 失去方向键与历史，交错从"覆盖"变"追加" |
| D 日志缓冲 + 空闲刷新 | `esp_log_set_vprintf()` 把日志收进 ringbuffer，REPL 空闲时刷出 | ~0.5d | 需处理溢出丢弃策略、锁、与 `idf.py monitor` 的时序 |
| E 物理分离 | console 走 USB-SERIAL-JTAG、日志走 UART0（或反之） | ~0.5d | 改变接线与自检方式（HARDWARE §8），需要两路串口 |
| F 换/自研 CLI | 自带日志仲裁的 shell | 高 | 收益低，不推荐 |

- **建议**：当前维持 A；P5（T5.1 console 补全）时若日志量已影响使用，优先评估 D（纯软件、不改接线），其次 E。
- **重新评估触发条件**：① P1 联网后日志频率导致输入基本不可用；② 需要脚本/产测自动解析 console 输出；③ 新增后台高频日志（WS 心跳、音乐状态、堆监控）。
- **参考**：`components/diag/diag.c`（printf 用于命令输出、ESP_LOG 用于事件，见该组件 README"关键约束"）；ARCHITECTURE §10.2；IDF `esp_console_repl_chip.c`（`uart_vfs_dev_use_driver`）、`linenoise.c`（重绘逻辑）、`log_write.c`（默认 `vprintf`）。

### X2 本地 mock 用 `ws://`、线上契约用 `wss://` 的证书验证策略（T1.5 起暴露）

- **状态**：待决策（不阻塞 T1.5；T1.4 `transport_ws` 开工时定，定了回填 §6 决策记录）
- **现象**：ARCHITECTURE §6.1 正式契约是 `wss://`，但本地 `tools/ws_mock_server.py` 为免证书负担用 `ws://`；端侧走 `wss://` 时 esp-tls 会校验证书链，本地自签证书不被信任，导致"本地能连、线上连不上"或反之。
- **影响**：T1.4/T1.6 若只实现 `wss`，本地无法联调（mock 无法出证）；若只实现 `ws`，线上不可用。TLS 还会占内部 RAM（ARCH §9.2 预算 ~45KB），需在 P1 基线里看到实际值。
- **候选方案**：

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| A 双传输 | `transport_ws` 同时支持 `ws://` 与 `wss://`，由 `CONFIG_AI_WS_URL` 的 scheme 决定 | 小（esp_websocket_client 本身支持，仅分支配置） | 生产固件保留 `ws` 分支 → 必须在发布检查里强制"量产只用 `wss://`" |
| B 自签 CA 烧入开发固件 | mock 用 openssl 自签，开发固件嵌入该 CA，由 Kconfig 开关切换 | 中 | 开发/生产证书管理分叉，多一步烧录流程 |
| C 开发期跳过校验 | `esp_tls` 关证书校验（仅开发构建） | 小 | 开发开关易漏到量产，必须 Kconfig 默认 n + 发布清单核对 |

- **建议**：A（双传输，scheme 决定）+ 发布检查强制 `wss://`；本地 mock 保持 `ws://` 零证书负担。B 只在需要验证 TLS 内存/证书过期路径时再做。
- **重新评估触发条件**：① T1.4 开工；② 需要实测 TLS 内存占用或证书过期/SNTP 时序；③ 后端要求 mTLS 或改用非 443 端口/自签网关。
- **参考**：ARCHITECTURE §6.1、§9.2、§10.1；`tools/ws_mock_server.py`、`tools/README.md`；PROTOCOL.md 待确认项 P-7。

### X3 内部 RAM 预算口径与 WiFi/WS/TLS 内存（T1.3 实测暴露，暂缓优化）

- **状态**：已记录、**暂缓优化**（2026-10-31 决策：功能优先，先完成 P1–P3，统一优化排在 P2 前评估）
- **现象（T1.3 真机实测，2026-10-31）**：
  - 引入 WiFi 后内部 RAM 一次增约 **110.9KB**：静态 DIRAM 138,070→189,834 B（+51,764）、堆峰值 133,460→192,572 B（+59,112）；
  - 应用可用内部 RAM 池（静态 DIRAM + 堆总量）= **457,161 B**；峰值占用 382,406 B（**83.6%**）；空闲堆 79,459 B，但**最大连续块只有 31,744 B**（T1.2a 时为 118,784 B）；
  - T1.4 预算 TLS ~45KB + WS ~24KB ≈ 70KB → 纸面余量不足、最大块也不够 TLS 缓冲。
- **静态增量的组件账**（map 对比 T1.2a）：`libpp` +18.1KB、`libnet80211` +12.6KB、`libphy` +8.4KB、`liblwip` +3.8KB、`libfreertos` +3.1KB、`libwpa_supplicant` +1.3KB、`libesp_timer` +1.2KB、`libesp_wifi` +0.9KB，其余 ~1.6KB。
- **堆增量的归因**：新增 5 个任务栈 19,456 B（`wifi` 6656 / `sys_evt` 4096 / `esp_timer` 3584 / `tiT` 3072 / `Tmr Svc` 2048）+ WiFi 静态 RX 缓冲 10×1.6KB≈16,000 B + 其余 ~23.6KB（mgmt 缓冲、动态 RX/TX 池、WPA/lwIP/netif/SNTP）。
- **根因**：
  1. ESP-IDF WiFi 栈固有约 110KB 内部 RAM（驱动/PHY/802.11/WPA/lwIP 静态 + 任务栈 + 缓冲），不是泄漏或配置错误；
  2. 用的是 IDF **高吞吐默认缓冲**：动态 RX/TX 各 32、静态 RX 10、RX/TX BA 窗口 6、mgmt sbuf 32，对"上行 Opus 4KB/s + 下行 TTS 3KB/s"偏大；
  3. **预算口径问题**：ARCH §9.2 的 310KB 写于 P0，只算了 TLS/WS、未含 WiFi 栈本身；且 STATUS 基线的"内部 RAM 峰值"只统计堆（不含静态），与"静态+堆峰值"口径相差约 190KB，两种口径必须拍板统一。
- **候选方案**：

| 方案 | 做法 | 预期收益 | 代价/风险 |
|---|---|---|---|
| A 裁剪 WiFi 缓冲 | 静态 RX 10→6、动态 RX/TX 32→16、mgmt sbuf 32→16 | −6.4KB 确定 + 峰值最多 −25KB×2 | 低；小流量够用，需 T1.6/T2 实测吞吐与环回 |
| B 缩小 TLS 缓冲 | `MBEDTLS_SSL_IN_CONTENT_LEN` 16K→8K、`OUT` 4K→2K | −10KB（握手期） | 低；需确认服务端单帧不超过 8KB（音频走二进制帧，文本帧很小） |
| C WiFi/lwIP 移 PSRAM | `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` | −30~50KB | 中；PSRAM 访问可能加链路时延，必须用 mock 实测 RTT/首包 |
| D WS 发送队列缩小 | T1.4/T2.5 的发送环从 24KB 设计改为 8KB（PSRAM） | −16KB 内部 RAM（若原计划内部） | 设计约束，需改 ARCH §9.2 |
| E 重定预算口径 | 明确"静态 DIRAM + 堆峰值 ≤ 目标值"并更新 ARCH §9.2/CONVENTIONS §4 | 0（只是对齐事实） | 需拍板目标值；预计 P2 全量后目标约 430~450KB |

- **建议**：功能完成后按 A→B→（不够再 C）顺序做一轮统一优化，同时把预算口径改成"静态+堆峰值"重新定目标；A 中"静态 RX 10→6"零风险，可先做。
- **重新评估的触发条件**：① T1.4 TLS 握手失败 / `sys heap` 空闲或最大块不足；② T1.6 记录 P1 基线时；③ P2 流式 TTS/Opus 使峰值再涨；④ 24h 压测出现碎片化或分配失败；⑤ 计划启用 OTA/双 TLS 等额外常驻内存。
- **参考**：ARCHITECTURE §9.2、CONVENTIONS §4；STATUS.md T1.3 行与 §5 基线；实测方法 `idf.py size-components --format csv` + 设备 `sys heap`/`sys tasks`；X2（TLS 策略）。
